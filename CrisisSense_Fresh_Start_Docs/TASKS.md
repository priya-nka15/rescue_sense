# Task Breakdown and Acceptance Criteria

## Workflow rules
Complete one phase at a time. Do not start the next phase until the current acceptance gate is reviewed. Each task should identify owner, evidence, tests, and manual actions. No phase is considered complete merely because files were created.

## Phase 0 — Read-only baseline and feasibility audit
**Tasks**
- Inspect current repository and Git status.
- Confirm whether repository is genuinely empty/new and preserve any existing files.
- Record Ubuntu/Python/Git versions, RAM/swap, free disk, and available runtime.
- Identify network constraints and whether any dataset/model files already exist.
- Do not install, download, edit, reset, or commit.

**Acceptance criteria**
- Audit report contains exact command outputs or reliable summaries.
- Existing work and uncommitted changes are preserved.
- Constraints and blockers are explicit.
- No files changed and no downloads/installs occurred.

🟥 **MANUAL — YOU MUST DO THIS:** Run any commands the agent cannot execute on your actual machine and share outputs.

## Phase 1 — Research question and related-work review
**Tasks**
- Search original papers and official repositories for crisis media verification, out-of-context media, multimodal disaster analysis, event-context consistency, and recycled media.
- Build a comparison table: task, dataset, labels, method, evaluation, limitation, overlap with CrisisSense.
- Identify candidate research gap and alternative narrower questions.

**Acceptance criteria**
- Important claims have traceable original citations.
- Candidate gap is phrased as a hypothesis, not a novelty assertion.
- A supervisor/research owner can approve one primary research question.
- No implementation begins before this review is assessed.

## Phase 2 — Dataset and label feasibility
**Tasks**
- Check official access, license, size, provenance, labels, data format, redistribution rules, and any restrictions.
- Verify whether data has real text-image/audio/video links or only separate modality datasets.
- Define annotation rules for consistency, contradiction, and insufficient evidence.
- Design train/validation/test splits; check event overlap and exact/near duplicates.

**Acceptance criteria**
- Dataset inventory records source URL, version/date checked, license, size, label mapping, modalities, access conditions, and risks.
- No fabricated modality pairings.
- Evaluation split strategy is documented before model selection.
- Required data is accessible within storage/compute limits, or scope is revised explicitly.

## Phase 3 — Environment and minimal repository setup
**Tasks**
- Choose supported Python version only after dependency compatibility review.
- Create minimal project structure, `.gitignore`, environment instructions, and smoke test.
- Keep ML packages out until needed.

**Acceptance criteria**
- Setup instructions work on a clean environment.
- Basic tests pass.
- No secrets, datasets, caches, model weights, or environment directories are tracked.
- Disk use is recorded and within the approved budget.

## Phase 4 — Baselines, one at a time
**Tasks**
- Implement the simplest valid baseline for each task supported by data.
- Begin with text TF-IDF + Logistic Regression/Linear SVM if the labels support it.
- Add image/audio/video baselines only when suitable data and task labels exist.
- Save split IDs and experiment configuration.

**Acceptance criteria**
- Metrics are generated by actual execution.
- Test set is not used for model selection.
- Preprocessing is fitted on training data only.
- Per-class metrics, confusion matrix, and error examples are reported.
- Runtime and memory use are recorded.

## Phase 5 — Proposed verification method
**Tasks**
- Define evidence representation and decision rules.
- Separate evidence for and against a claim from missing evidence.
- Compare a simple fusion baseline with the proposed method.
- Include abstention/insufficient-evidence behavior.

**Acceptance criteria**
- Method is specified precisely enough to reproduce.
- No modality is treated as independent corroboration if derived from another (e.g. sampled video frames).
- Evaluation labels are independently justified.
- Method is compared against suitable baselines and ablations.

## Phase 6 — Robust evaluation
**Tasks**
- Run frozen final test evaluation after method selection.
- Test event-disjoint generalisation where feasible.
- Check duplicates, class imbalance, failure cases, missing modalities, and uncertainty.
- Add confidence intervals or repeated runs where computationally reasonable.

**Acceptance criteria**
- All reported metrics trace to saved predictions and a fixed test manifest.
- Baselines and proposed method use comparable evaluation conditions.
- No unsupported superiority or novelty claims.
- Limitations and negative findings are documented.

## Phase 7 — API and interface
**Tasks**
- Implement an API only after the inference contract is known.
- Add input validation, bounded processing, explicit unsupported/error states, and structured evidence output.
- Add a minimal UI only if it helps demonstrate the research.

**Acceptance criteria**
- API schema is documented and tested.
- Malformed, oversized, unsupported, and missing inputs are handled safely.
- The UI never presents model output as confirmed fact.
- API integration tests pass.

## Phase 8 — Reproducibility, paper, and release
**Tasks**
- Document exact environment, data versions, checkpoints, configurations, seeds, and commands.
- Review licensing, privacy, and citations.
- Prepare methodology/results/limitations and figures from actual outputs.

**Acceptance criteria**
- A fresh environment can reproduce the documented pipeline within stated constraints.
- Every table and claim traces to source or experiment output.
- No secrets or restricted data are published.
- Paper accurately reports limitations and does not overstate deployment readiness.
